## Priority findings

### P0 for local authenticated QA — Google rejects the test origin

The supplied popup screenshot explicitly reports `origin_mismatch` and asks the developer to register the JavaScript origin. In Google Cloud, find the Web OAuth client matching `VITE_GOOGLE_CLIENT_ID` and register the exact test origin under Authorized JavaScript origins: `http://127.0.0.1:5173`. If using `http://localhost:5173`, authorize that separately; the hostnames are distinct origins. This is not a redirect-URI error. The OAuth configuration was not changed in this review.

Source: [Google Identity Services setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).

### P1 — Refresh silently loses unlogged practice time

Reproduction: sign in; start the ten-minute interval; advance about 65 seconds; pause; reload; sign in again. The timer returns to 10:00 and saved hours remain empty.

Cause: `serializeProgress` excludes timer state. `savePending` compares only that serialized progress, so elapsed timer time alone does not trigger the unload warning. Sign-in reconstructs a fresh timer.

Fix: persist recoverable elapsed session state or checkpoint credited time without double counting. Include uncredited practice in the unsaved-work guard. Test running, paused, expired and already-logged timers across reload. Suggested skill: `/harden`.

### P1 — Save conflicts offer a recovery action that cannot recover

Reproduction: sign in against revision 0; simulate another device saving revision 1; edit a note; click Retry save after failure. The same failure remains and the note is absent from the saved account data.

Cause: retry resends the unchanged `cloudVersion`. Only successful writes advance it. The generic error message hides the distinction between a temporary network failure and a permanent revision conflict.

Fix: distinguish conflict errors, fetch current progress, retain the local draft, and offer an explicit reconciliation path. Do not simply overwrite the server revision or discard the pending draft. Suggested skill: `/harden`.

### P2 — Focus Mode hijacks normal keyboard button activation

Reproduction: open Focus Mode; focus Exit Focus; press Space. Focus Mode stays open and the timer starts.

Cause: its window key handler prevents Space on buttons, unlike the main app handler. Other Focus Mode buttons are subject to the same interception.

Fix: preserve native activation on interactive elements; ignore modified and repeated shortcuts. Give the checklist buttons accessible labels and checked state; they are currently empty buttons. Suggested skill: `/harden`.

### P1 — Mobile puts starting practice after finishing practice

The phone screenshot places three lesson cards, the notes form, Mark Day Complete and two export actions before the timer. Start is well below the first viewport. The existing mobile test only checks horizontal overflow, so it cannot catch this usability problem.

Fix: place the active part and Start near the session heading on small screens; keep notes and completion after practice. A compact sticky timer can preserve access while reading. Verify at phone and portrait-tablet sizes. Suggested skill: `/adapt`.

### P2 — Focus Mode removes the context needed to practise

Its largest area is an empty image upload surface. The session rail shows only part names and short purpose lines; detailed instructions, exercise links and interval selection are missing. On Day 1, a learner must leave Focus Mode to reread the actual drill or choose the next part's timer.

Fix: show the current exercise instructions and a next-part action beside the timer. Make the reference surface optional and compact when empty. Suggested skill: `/distill`.

## Visual critique

Anti-pattern verdict: mixed. The condensed display typography and restrained orange accent give it a recognizable training identity. It avoids gradient/glass decoration. However, nearly every section uses a rounded card, exercise cards rely on thick colored left borders, and small all-caps condensed subheads are harder to scan than body text. Simplify containers and reserve the display face for large headings.

What works:

- Warm-up → drill → project gives the session a clear learning structure.
- Desktop separates lesson instructions and timer effectively.
- Visible part durations and the highlighted Start button make the timer understandable once found.

The sign-in screen has one clear action, but resembles a modal over an empty grey page. It gives almost no explanation of the eight-week course, expected commitment, or account saving. A short welcoming entry page would explain the value before asking for sign-in.
